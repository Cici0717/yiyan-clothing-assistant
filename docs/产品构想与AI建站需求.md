# 服饰百科与网购助手_完整产品构想与AI建站需求

> 本文基于 2026-09-29 的产品想法交流整理，可整篇交给 AI，作为网页设计与开发的需求上下文。
>
> **范围说明：记录整个产品想法，覆盖全部功能方向，不将其收缩为第一版或仅有材质科普的页面。** 交流中讨论过从小范围起步，但那属于实施顺序建议，不代表删除完整愿景。本次仅形成需求文档，尚未创建网站。

## 1. 交给 AI 的任务说明

请根据本文设计并实现一个中文服饰百科与网购助手网站，帮助普通用户理解衣服的材质和标签，判断衣服的尺寸、长度、颜色和风格是否符合自己的需求，并通过购买与穿着记录积累个人经验。

产品暂用名为“服饰百科与网购助手”，正式名称可以调整。

请同时理解产品的两个用途：

- **学习与查询**：用户可以系统了解服饰知识，也可以搜索某个看不懂的词。
- **具体购物决策**：用户拿着一件商品的信息，能够理解它、与自己的需求和已有衣服比较，再决定是否购买。

完整产品需要覆盖材质百科、标签解读、个人需求与尺寸档案、服装长度及尺码参考、鞋子参考、配色与风格探索、购买和穿着记录。各模块应互相连通。

本文中的“用户明确提出”代表需求来源；页面名称、布局、数据字段和交互方案属于为便于落地补充的设计建议。可以优化实现方法，但应保留需求意图和功能范围。

## 2. 想法的来源与讨论链路

### 2.1 用户最初提出的问题

1. 网购时会遇到棉、丝绸等不同材质，希望把类别及特点整理清楚，方便了解和比较。
2. 商品标签和宣传名称容易混淆，例如“棉百分百”“百分百棉”等表达，让人难以判断信息是否可信，希望有规范解释和辨别思路。
3. 小红书和其他网站上存在大量关于身高、衣长、短袖、七分裤、长裤和鞋子的建议，希望汇总成方便查询的参考。
4. 希望知道哪些材质适合自己，以及什么长度、尺寸更符合自己的穿着需求，从而更方便网购。
5. 希望记录买过的衣服或裤子的材质、尺寸和舒适程度，方便以后参考、避开不满意的选择或回购。
6. 身体围度不容易确定。除了自己测量，也希望利用已经穿过的衣服、所穿尺码和实际反馈，逐步形成适合自己的参考。
7. 完整愿景还包括根据肤色探索适合的颜色和风格，并整理穿搭博主的相关经验。
8. 最终希望拥有一个兼具百科与个人参考价值的服饰网页。

### 2.2 交流中逐渐明确的设计判断

- 产品主线可以贯穿“看懂商品—了解自己—比较选择—记录穿着—为下次购买提供参考”。
- 科普内容与网购问题解决可以结合：知识提供判断依据，具体问题决定知识如何呈现。
- 材质知识应解释特点与取舍，避免简单给材质排好坏。
- 标签解读可以帮助理解名称、检查信息完整性和发现矛盾，但不能仅凭文字或照片鉴定实物成分真假。
- 长度与尺码建议应利用多种证据，并明确适用条件，不能只凭身高给出唯一答案。
- 用户已有的合身衣服，是建立个人尺寸参照的重要入口。
- 穿着记录应服务于下一次购买，逐步形成个人经验，而不只是保存商品清单。
- 配色与风格建议应提供探索空间，保留个人审美选择。

### 2.3 用户最后明确的文档范围

需要保存整个产品构想，并写成能够交给 AI 制作网页的内容。因此，本文件保留所有上述模块；后续如讨论实施顺序，应另行决定，不将早期的第一版建议视为最终范围。

## 3. 产品定位与使用对象

### 3.1 产品定位

一个面向日常网购的服饰知识与个人选购参考工具。用户既可以浏览百科，也可以围绕正在考虑的商品得到有依据、可理解的分析，并积累自己的穿着偏好。

核心价值是：

- 看懂商品名称、成分和标签，减少信息理解上的困难。
- 了解材质、尺寸、颜色及风格与个人需求之间的关系。
- 把零散的收藏、试穿和购买经验转化为下一次能使用的参考。

### 3.2 主要使用对象

- 经常网购服饰，但不熟悉纤维、面料和标签术语的人。
- 对舒适程度、衣长、裤长或松紧有偏好，却难以准确表达的人。
- 看过很多穿搭建议，希望整理成适用于自己的参考的人。
- 希望记住满意或不满意的购买经历，减少重复试错的人。

不预设固定性别、身高区间或身材类型；按服饰品类和真实需求组织功能。

## 4. 完整功能范围

### 4.1 材质与面料百科

**用户希望了解不同材质是什么、有什么特点、是否适合自己。**

内容结构建议区分：

- 纤维成分：例如棉、亚麻、蚕丝、羊毛、羊绒、粘胶、莫代尔、莱赛尔、聚酯纤维、锦纶、氨纶等。具体词条建立前逐项核实。
- 面料组织、加工方式及相关参数：解释它们如何与成分共同影响表现。
- 商品名称、常见叫法及商标名称：说明名称能提供什么信息，还需要查看什么。
- 混纺组成：支持多种成分和比例，避免只按占比最大的纤维解释整件衣服。

每个知识词条建议包含：

| 内容 | 用户可以得到什么 |
| --- | --- |
| 一句话解释与常见名称 | 快速知道这个词是什么意思 |
| 典型特点与条件 | 理解触感、吸湿、干燥、透气、弹性、保暖等相关表现，不将其视为所有商品的保证 |
| 主要取舍 | 了解舒适、外观、耐用和打理之间可能存在的取舍 |
| 场景参考 | 结合季节、活动和个人偏好理解适用情况 |
| 选购检查项 | 知道还需看哪些信息，例如织物结构、厚薄、里料、洗护说明 |
| 易混淆概念 | 区分成分、结构、加工和宣传用语 |
| 来源与更新时间 | 追溯结论，了解适用范围 |

交互建议：支持关键词搜索、同义词检索、分类浏览、收藏，以及在统一维度下并排比较材质。一般特性用文字及条件说明，未经数据支持不生成精确评分或排名。

### 4.2 标签与商品信息解读

**用户希望看懂宣传文案和成分标签，减少被模糊信息误导的可能。**

输入方式可以包括手动填写、粘贴商品描述，以及上传标签或详情页截图。图片识别是可接入能力，识别后应允许用户确认和修改原文字段。

输出应包括：

1. 原文与整理后的成分、比例、适用部位，例如面料、里料或填充物。
2. 名称解释，以及它属于成分、加工描述还是其他商品用语。
3. 信息是否完整，商品描述与标签之间是否存在需要确认的矛盾。
4. 能从现有信息判断什么，还有什么无法判断。
5. 可向商家进一步确认的问题。

明确的内容边界：

- 规范标注中的“100%棉”和“棉100%”不能因为文字顺序不同而被判为真假不同；“纯棉”“全棉”的解释应结合适用标准及其条件。[来源 1]
- 标注规范、标注内容与实物是否相符，是不同问题。网站可以解释前者、提示疑点，不能仅凭截图证明后者。
- “资料未提供”应显示为未知，不能自动解释成不合格或虚假宣传。
- 百分比检查必须按相同部位和范围进行，不把面料、里料、填充物混在一起相加。
- 保留原文和原图作为用户核对依据；识别或归一化后的结果不能覆盖原始内容。

### 4.3 个人需求、偏好与尺寸档案

**用户希望网页逐步了解自己，减少每次购买都从头判断的负担。**

档案建议包括：

- 使用场景：通勤、日常、居家、运动等。
- 舒适偏好：对闷热、扎肤、紧绷等体验的在意程度。
- 打理偏好：是否愿意熨烫、手洗或进行特殊洗护。
- 外观偏好：贴身、合体、宽松，以及希望衣服或裤脚落到的位置。
- 用户愿意提供的身体测量：身高、胸围、腰围、臀围等，按品类按需收集。
- 已有衣服参照：品牌、款式、尺码、实测尺寸和穿着反馈。
- 喜欢的颜色、搭配及风格。

不要求用户首次进入时填完整档案。允许“暂时不知道”，也允许先通过一件熟悉的衣服建立参照。记录每条尺寸的来源与测量时间，区分身体实测、衣服实测、商品尺码表和用户估计。

### 4.4 服装长度、尺码与版型参考

**用户希望知道短袖、七分裤、长裤等穿在自己身上可能是什么效果，以及怎样选择长度和尺码。**

应提供两条使用路径：

1. 根据用户填写的身体测量、穿着目标和商品信息进行比较。
2. 根据一件已知穿着效果的同类衣服进行比较，不强制先量身体。

建议按品类展示相关字段：

| 品类 | 参考信息示例 | 可解释的比较结果 |
| --- | --- | --- |
| 短袖及其他上衣 | 衣长、肩部结构、胸部尺寸、袖长、弹性及松紧偏好 | 与参照衣服相比长短、宽窄的差异，以及需要进一步确认的部位 |
| 七分裤及其他短、中长裤 | 腰部尺寸、臀部尺寸、裤内长或裤外长、裤裆和腰位信息 | 裤脚目标位置与尺寸的关系，说明仅有名称时的信息限制 |
| 长裤 | 腰部、臀部、裤内长或裤外长、裤型、腰位，以及搭配鞋子的情况 | 长度及松紧比较，提示可能需要试穿或修改的地方 |

设计原则：

- 身高提供初步线索，不生成“某身高唯一适合某衣长”的普遍结论。
- 区分身体围度与成衣尺寸，区分平铺宽度与整圈围度。
- 统一单位和测量口径，展示测量方式。不同口径不直接计算差值。
- 商品数据必须关联具体品牌、款式及尺码；不同商品的 M 码不能直接视为等价。
- 版型、弹性、穿着方式及洗后变化会影响解释，缺少信息时说明限制。
- 用户穿过的尺码和反馈可以帮助比较，但不能反推出唯一、精确的身体围度。
- 可以逐步归纳“满意衣服的尺寸范围”，同时保留品类和版型条件，显示记录数量。

示例：参照 T 恤衣长为 62 厘米，用户反馈长度满意；待购 T 恤在相同测量口径下衣长为 66 厘米。网站可以明确显示“比你的参照 T 恤长 4 厘米”，同时结合版型提示解释边界。此处数字仅用于交互演示，不代表对任何真实用户的推荐。

### 4.5 鞋子选购与搭配参考

**鞋子属于用户最初提出的完整范围，需要保留。**

建议分成两个相关用途：

- 合脚参考：结合用户愿意提供的脚长、脚宽、已有鞋款及穿着感受，比较目标鞋款的尺码信息。
- 搭配参考：结合裤型、裤长、场景和用户偏好，展示鞋子搭配思路。

已有鞋子可记录“前掌偏紧、脚跟不稳、长度满意”等反馈。商品比较应区分脚长、鞋内长、鞋垫长度和尺码标注，缺少测量定义时不强行换算。保留不同品牌、款式和鞋型之间的不确定性。

### 4.6 肤色、配色与风格探索

**用户希望探索适合自己的衣服颜色和风格，并整理穿搭博主的经验。**

建议功能：

- 通过文字、色卡或搭配示例了解用户喜欢的效果、颜色、场景和风格。
- 将用户自述的肤色相关信息作为参考之一，允许不确定或跳过。
- 展示多组可尝试的配色与搭配，说明建议依据，允许收藏和表达喜欢或不喜欢。
- 记录用户实际尝试后的反馈，逐步形成个人偏好。
- 保留穿搭经验的原链接、作者、适用条件和整理说明。

肤色建议不应成为硬性穿衣限制，也不对用户的肤色、身材或审美作高低评价。照片分析可作为待评估能力，用户自愿提供，说明光线与设备会影响颜色呈现，不能将照片结果包装成客观且唯一的分类。

小红书和其他网站的内容应作为需要整理、注明出处的经验材料；不要把某位博主的偏好自动升级为通用结论。用户尚未指定具体博主、账号或授权材料。

### 4.7 我的衣服与穿着记录

**用户希望记录买过什么、穿起来怎样，以及以后是否值得回购。**

每件衣服或鞋子的记录建议包括：

| 字段组 | 建议内容 |
| --- | --- |
| 商品识别 | 品牌、款式、品类、购买尺码、链接、照片、购买日期 |
| 材质信息 | 标签原文、分部位成分与比例、已知面料信息 |
| 尺寸信息 | 商品表数据、用户实测、测量口径及日期 |
| 合身反馈 | 偏长或偏短、偏紧或偏松，以及具体部位 |
| 舒适反馈 | 闷热、扎肤、紧绷、活动是否方便等感受 |
| 使用条件 | 季节或天气、通勤或运动等场景、穿着方式 |
| 洗后表现 | 缩水、变形、起球等实际观察及洗护方式 |
| 最终判断 | 满意程度、是否愿意回购、原因和备注 |

支持新增、修改、删除、检索、筛选，以及将一件满意的衣服设为比较参照。允许同一件衣服有多次穿着或洗后记录，不覆盖以前的体验。

录入尽量轻量：先选择少量直观选项，详细信息选填。保存商品标识与照片，以便原链接失效时仍能理解历史记录。

个人结论应由记录支持。例如“你记录过的三件同类上衣中，两件衣长接近的款式获得了满意评价”。不能把一次不舒服归因于某一种纤维，也不能由少量记录生成确定的个人体质判断。

## 5. 页面结构与模块联动建议

采用适合手机查询、同时支持电脑浏览的响应式网站。完整范围可以由以下页面承载，具体导航名称允许调整。

| 页面 | 主要内容 | 关键联动 |
| --- | --- | --- |
| 首页与搜索 | 按“查一个词、看懂标签、比较一件衣服、找穿搭参考、记录穿着”进入 | 跳转相应任务，保留用户输入 |
| 材质百科与词条详情 | 分类、搜索、特点、取舍、来源、材质比较 | 从词条进入标签或商品分析 |
| 标签与商品解读 | 输入描述或图片，校正字段，查看解读 | 关联材质词条、个人档案和尺寸比较 |
| 服装尺寸与长度参考 | 选择品类、身体或衣服参照、目标效果、目标商品 | 使用已有衣服，查看差异并保存记录 |
| 鞋子参考 | 合脚信息、历史鞋款、场景和搭配 | 关联裤装及个人穿着反馈 |
| 配色与风格探索 | 偏好选择、搭配示例、来源、收藏和尝试反馈 | 关联个人偏好和已有衣服 |
| 我的档案 | 场景、偏好、可选测量及来源 | 为各类比较提供用户背景 |
| 我的衣服与记录详情 | 商品资料、历次反馈、参照设置、回购意向 | 用历史经验帮助新商品比较 |

导航可以分组，不要求在手机顶部同时展示所有入口。知识内容应能够直接浏览，个性化功能按需补充档案。

## 6. 需要贯通的使用流程

### 流程 A：从看不懂材质到理解商品

用户搜索一个词或输入商品描述 → 查看名称与成分解释 → 根据自己在意的需求查看取舍 → 发现还缺少的信息 → 带着明确问题继续了解商品。

### 流程 B：从已有衣服到比较新商品

用户选一件满意的已有衣服 → 读取其尺寸和反馈 → 输入目标商品对应尺码表 → 校对测量口径 → 查看长短和宽窄差异及限制 → 保存目标商品资料，后续补充真实穿着反馈。

### 流程 C：从收货体验到下次购买参考

用户保存商品 → 记录初次试穿 → 穿着或洗涤后追加观察 → 形成有条件的个人偏好 → 下次比较时引用这些记录，并允许用户纠正。

### 流程 D：从配色建议到个人审美积累

用户表达场景与喜好 → 浏览注明来源和条件的搭配建议 → 收藏或尝试 → 记录感受 → 后续优先展示与个人偏好相关的方案，同时保留探索其他风格的入口。

鞋子既可以独立查询，也可以在裤装长度与搭配流程中作为参考，不要求用户每次都填写鞋子信息。

## 7. 内容与推荐的可信度要求

### 7.1 不同信息承担不同作用

| 信息类型 | 主要作用 | 展示要求 |
| --- | --- | --- |
| 标准、监管说明及专业资料 | 解释定义、规范和适用条件 | 标明出处、版本或日期，核对生效状态 |
| 品牌及商品信息 | 描述具体商品的成分、尺寸和洗护说明 | 标明商品和来源，不默认为独立检测结果 |
| 博主和其他穿搭经验 | 提供搭配灵感与经验参考 | 标注作者、原链接和适用情境 |
| 用户自己的记录 | 描述这个用户在特定条件下的真实感受 | 保留日期、场景和具体商品 |
| 系统建议 | 解释上述资料与当前需求的关系 | 说明依据、缺失信息和不确定性 |

### 7.2 内容整理与维护

- 知识词条需记录来源、核验日期和适用范围。标准应区分当前生效、已发布未实施及草案等状态。
- 不直接复制大量平台文章或图片。优先用自己的表述整理要点，保留出处；展示图片时确认使用条件。
- 商品截图、博主经验和示例内容不能自动成为已核验的知识。
- 未核实的内容标注待核实，事实冲突保留不同来源及其条件。
- 对纤维的一般描述与具体成衣的表现分开，避免“某成分一定舒服”或“某材质永远更好”。
- 配色、风格和舒适偏好允许主观差异；不伪造“最适合”的确定答案。

### 7.3 推荐说明的统一结构

每条个性化建议应尽量回答：

1. 目前可以判断什么。
2. 依据哪些商品信息、用户记录或知识来源。
3. 还缺少什么，这会影响哪些判断。
4. 用户下一步可以补充什么或比较什么。

没有足够数据时，仍可提供通用说明或客观差异，明确个性化判断的限制。不生成没有校准依据的精确匹配概率。

## 8. 供开发使用的数据结构建议

以下是概念层面的结构，不限定数据库、框架或服务商。

| 数据对象 | 核心信息 |
| --- | --- |
| 知识词条 | 标准名称、别名、类别、特点及条件、易混淆项、关联词条、来源、核验日期 |
| 来源 | 标题、作者或机构、链接、发布日期、来源类型、适用范围及核验状态 |
| 商品 | 品类、品牌、款式、尺码、链接、照片、分部位成分、尺寸、洗护信息、原始资料 |
| 测量值 | 项目、数值、单位、身体或成衣、平铺或围度等口径、来源、日期 |
| 个人档案 | 可选身体测量、场景、松紧与长度偏好、舒适与打理偏好、配色与风格偏好 |
| 穿着记录 | 关联商品、时间、场景、具体部位反馈、舒适感受、洗后观察、回购意向 |
| 搭配参考 | 场景、颜色、风格、适用条件、来源、用户喜好及尝试反馈 |
| 比较结果 | 输入快照、参照商品、维度差异、依据、缺失信息、用户修正 |

记录需能持续保存，刷新页面后仍可恢复。个人尺寸、照片及穿着记录默认作为私人资料，用户应能够修改、删除和导出。演示内容与用户自己的数据应明确区分。

## 9. 界面与交互方向

以下为设计建议，用户尚未指定视觉稿或品牌风格。

- 整体清晰、易读，有适度的服饰与生活感；通过留白、材质示意、尺寸示意和配色卡帮助理解。
- 先给简明解释，再展开详细依据，降低第一次使用的学习成本。
- 重要比较采用并排卡片、差异表或示意图，避免用户来回翻页记数字。
- 表单按当前品类显示相关字段，允许跳过未知信息。
- 示意图标明是参考图，不能伪装成基于真实测量的试穿结果。
- 显示明确的加载、空数据、识别失败、保存失败及数据不足状态，并提供可继续操作的入口。
- 基本文字和控件可读，键盘能够完成主要操作，颜色区别同时配合文字说明。
- 页面文案使用普通用户能理解的语言，专业词汇可以点开解释。

## 10. AI 能力与实现要求

### 10.1 适合引入 AI 的环节

- 从用户提供的标签或商品截图提取信息，供用户确认。
- 将商品名称和成分用语关联到已核验词条。
- 根据知识、商品信息和个人记录生成有来源的解释。
- 整理用户反馈中反复出现的偏好，并让用户确认。
- 在已有可靠资料范围内回答服饰问题。

### 10.2 需要明确区分的能力

- 单位换算、尺寸差值和记录保存等使用明确规则完成。
- AI 可以协助解释，不能凭空补出商品克重、纤维比例、品牌尺码或用户身体数据。
- 没有接入图片识别、网站导入或 AI 服务时，应明确显示该能力的实际状态，提供手动输入路径，不模拟已完成真实识别。
- 商品链接可以用于保存和打开原页面；自动读取电商或社交平台内容需要另行确认可用来源与接入方式，不默认所有链接都能自动解析。
- 全部功能方向应在产品架构和设计中保留。如需要分步实现，应列明哪些已实现、哪些是有说明的演示、哪些尚待接入，不能把完整需求悄悄缩成一个静态科普首页。

技术框架、账号体系、数据同步方式、模型供应商和部署方式尚未确定。实施时根据实际环境选择；本需求不强制特定技术栈，也不要求为实现完整愿景一次性接入所有外部平台。

## 11. 完整产品的验收依据

以下用于检查完整愿景是否得到落实，不代表已经完成这些能力。

- [ ] 用户可以按名称或别名检索材质，阅读有来源的解释，并比较主要特点和取舍。
- [ ] 用户可以看懂成分标签中的名称、比例和部位，知道哪些信息仍需确认。
- [ ] 不因“100%棉”和“棉100%”的顺序不同而生成真假判断。
- [ ] 用户可以按需建立个人偏好和尺寸档案，并允许未知字段。
- [ ] 用户可以选择身体数据或已有衣服作为参照，比较目标商品尺寸。
- [ ] 平铺与围度、厘米与其他单位、裤内长与裤外长等不会在未校对时被混算。
- [ ] 服装参考覆盖短袖、七分裤、长裤等用户提出的方向，并能解释条件和限制。
- [ ] 鞋子有独立的合脚与搭配参考位置，能使用已有鞋款反馈。
- [ ] 配色与风格功能允许表达偏好、查看出处、收藏和反馈，不给出强制审美结论。
- [ ] 用户可以新增、修改、删除和找回商品与穿着记录，刷新后数据仍然存在。
- [ ] 真实用户资料与演示数据有清楚的界限。
- [ ] 历史穿着记录能进入后续比较流程，建议能追溯到具体依据。
- [ ] 信息不足、识别失败或外部服务未接入时，页面如实说明并提供替代操作。
- [ ] 手机和电脑均能完成主要任务，页面间的数据与跳转连贯。

## 12. 尚未决定的事项

这些问题保留给后续产品设计，不将助手的建议当作用户已作出的决定：

- 正式名称、视觉风格和品牌表达。
- 首批重点覆盖的服饰品类，以及专业内容的核验方式。
- 是否需要账号和多设备同步，个人数据如何保存。
- 是否接入图片识别、照片辅助配色、自动读取商品链接等能力。
- 具体采用哪些博主、机构、品牌或其他内容来源。
- 是否发展商品导购或商业化功能；目前没有这方面的明确需求。
- 开发资源、时间安排、技术栈和部署环境。

后续可以讨论实施顺序，但应以这份完整构想为依据，保留各模块之间的联系。

## 13. 给建站 AI 的交付要求

阅读整篇文档后，请先确认你理解的是完整产品愿景，再完成设计与实现。交付应包括：

1. 简明的产品结构与页面关系，说明各入口如何帮助用户完成任务。
2. 可使用的网页及主要交互，覆盖本文列出的完整功能方向。
3. 可追溯的知识内容和明确标注的演示数据，不编造材料结论、用户历史或商品信息。
4. 可持续保存和管理个人资料、商品及穿着记录的方案。
5. 对实际能力的说明：已实现的功能、尚未接入的能力及其替代操作。
6. 依据第 11 节进行主要流程验证，并交代仍未满足的项目。

界面可以简洁，解释可以分层，但不要只完成展示页而遗漏用户查询、比较、记录和再次使用的流程。若本轮交付资源不足以完成全部功能，先明确具体交付范围及剩余项，完整构想仍以本文为准。
